Cultural evolution

From DevOps to DevSecOps

Security is no longer a step at the end and is now born along with the code: shift-left, automation, and quick feedback.

DevOps accelerated delivery, but for a long time security continued in the model of waiting for the software to be ready to test. DevSecOps changes this: security participates from the beginning and must be automated. The goal is not to install another manual gate; it's to put controls into the engineering flow.
DevOps → DevSecOps

Why integrate security?

  • Find problems while the team is still designing and developing.
  • Reduce rework and shorten the path between discovery and remediation.
  • Deliver quickly, with security as a shared responsibility.

Secure Software Development Life Cycle

Security throughout the lifecycle

1
PlanThreat modeling, requirements, and risk criteria.
2
CodeSAST, secrets, and pull request feedback.
3
BuildSCA, SBOM, images, and dependencies.
4
TestDAST, security testing, and staging.
5
OperateObservability, response, and learning.
The goal is not to “test security at the end”. It is to create continuous feedback where the decision happens.
In S-SDLC, each phase has appropriate controls. In planning, we model threats. In coding, we analyze vulnerabilities and secrets. In build, we look at dependencies and images. In staging, we do dynamic testing. In operation, we monitor and learn. The central point is to reduce the time between introducing a risk and receiving useful feedback.

Coding stage - Third-party code

SCA · dependencies

  • Analyze libraries and components used by the application.
  • Identify dependencies with known vulnerabilities.
  • Evaluate the update and validate the effect of the fix.
  • In the demonstration: Trivy.
The original slide relates SCA to A06:2021 — Vulnerable and Outdated Components. SCA analyzes components; it is a separate activity from manual code review.
Coding stage - Your own code

SAST · source code

  • Look for potentially insecure code patterns.
  • Review inputs, dangerous calls, and configurations.
  • Investigate findings with code context.
  • In the Python demonstration: Bandit.

Open source stack

Tools entering the pipeline

TM

Map flows, assets, trust boundaries, and abuse scenarios before the code.

S

Static analysis to locate insecure patterns and problems in the code.

KEY
TruffleHog / Gitleaks

Detect credentials, tokens, and secrets exposed in the repository.

IMG
Trivy

Vulnerabilities in containers, operating system, packages, and repositories.

Complement: automated scripts and dynamic scanners to validate the running application.

This is where open source tools come in. Threat modeling starts before the code. In the pipeline, we can use Bandit for Python/SAST, TruffleHog or Gitleaks for secrets, and Trivy for containers, packages, and repositories. Then, in the test environment, scripts and dynamic scanners expand coverage.

Paradigm shift

When coding is no longer the bottleneck

10×

More code generated in less time also means more surface to review.

Copilots and agents accelerate implementation. Manual security review doesn't scale at the same speed.
Reference used in the material: The AI-Native SDLC Playbook — Anthropic
With generative AI, writing code became much faster. The 10× number here is visual and represents the magnitude shift — not a universal metric. The point is: if code production accelerates and human review remains linear, the bottleneck moves. We need to apply automation and context also in the analysis of findings.

Imagine 120 findings coming from various scanners. Instead of putting 120 items in the human queue, we can correlate the results with the change, the application's exposure, and the asset's context. The 120 to 5 is a didactic example, not a promise of fixed reduction. Human review remains essential in relevant cases.
New operational design

How AI changes S-SDLC

Planning

Living artifacts of intent — such as intent.md — help humans and agents share context, constraints, and security criteria.

Development

AI helps draft test cases, negative scenarios, validations, and evidence alongside implementation.

Governance

Scanners remain objective; AI aids in triage; people focus energy on critical code, architectural decisions, and real risk.

AI doesn't remove S-SDLC. It changes where humans add the most value.
In planning, artifacts of intent can carry context for both humans and agents. In development, AI can help generate tests and negative scenarios. In governance, scanners continue to produce objective signals, while AI assists in triage. A person no longer spends time equally on everything and focuses on the most critical cases.
